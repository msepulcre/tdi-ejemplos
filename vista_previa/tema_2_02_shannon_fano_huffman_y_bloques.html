Shannon–Fano y Huffman: evaluar códigos dados y cambios en la fuente¶

Tema 2 · Apartados 2.3–2.4 · Demostración orientativa: 10–20 minutos.

Resolver un problema de eficiencia, desajuste del modelo y coste de enviar el libro de códigos.

Modelo y pregunta¶

Una fuente tiene cinco símbolos. Para la distribución de diseño $q=(0.40,0.15,0.15,0.15,0.15)$ se han obtenido estos códigos dados:

Símbolo q de diseño Huffman Shannon–Fano Longitud fija
a1 0.40 0 00 000
a2 0.15 100 01 001
a3 0.15 101 10 010
a4 0.15 110 110 011
a5 0.15 111 111 100

Estudiamos $L=\sum_i p_i l_i$, la redundancia $L-H(X)$ y la eficiencia $H(X)/L$. No se construyen códigos nuevos: las palabras de la tabla permanecen fijas durante el experimento. Si la distribución real $p$ cambia, el código diseñado mediante Huffman para $q$ puede dejar de ser compacto para $p$. Su nombre identifica su origen, no garantiza que siga siendo óptimo.

Variamos la frecuencia del primer símbolo y repartimos el resto por igual: $$p=(p_1,(1-p_1)/4,(1-p_1)/4,(1-p_1)/4,(1-p_1)/4).$$ Esta familia permite resolver analíticamente cuándo conviene cada código dado.

import math
import html

                     'axes.spines.right': False})
AZUL = '#006d75'
NARANJA = '#b95028'
GRIS = '#617583'

def tabla(cabeceras, filas):
    def celda(x):
        return html.escape(str(x))
    cuerpo = ''.join('<tr>' + ''.join('<td>' + celda(x) + '</td>' for x in fila)
                     + '</tr>' for fila in filas)
    display(HTML('<div style="overflow-x:auto"><table><thead><tr>'
                 + ''.join('<th>' + celda(x) + '</th>' for x in cabeceras)
                 + '</tr></thead><tbody>' + cuerpo + '</tbody></table></div>'))

def entropia(prob):
    p = np.asarray(prob, dtype=float)
    p = p[p > 0]
    return float(-np.sum(p * np.log2(p)))

2. ¿Cuándo cambia el código que conviene usar?¶

Para esta familia de fuentes, basta sustituir en la suma ponderada: $$L_{\mathrm H}=p_1+3(1-p_1)=3-2p_1,$$ $$L_{\mathrm{SF}}=2p_1+\frac{2+2+3+3}{4}(1-p_1)=2.5-0.5p_1.$$ Se igualan en $p_1=1/3$. Estas curvas evalúan las dos asignaciones de la tabla; no son las prestaciones de algoritmos que vuelvan a calcular el código para cada punto.

ps = np.linspace(.05, .95, 401)
LH = 3-2*ps
LSF = 2.5-.5*ps
Hs = np.array([entropia([x]+[(1-x)/4]*4) for x in ps])
fig, ax = plt.subplots(figsize=(9, 4.5), layout='constrained')
ax.plot(ps, LH, color=AZUL, label='Huffman dado, diseñado para q')
ax.plot(ps, LSF, color=NARANJA, label='Shannon–Fano dado, diseñado para q')
ax.plot(ps, Hs, ':', color='#805b96', label='Entropía de la distribución actual')
ax.axhline(3, ls='--', color=GRIS, label='Código de longitud fija')
ax.axvline(1/3, ls=':', color=GRIS, label='Igualdad de los dos códigos: p1 = 1/3')

3. Un paquete corto también paga la cabecera¶

Supongamos que para usar uno de los códigos variables hay que enviar $B$ bits adicionales de modelo o libro de códigos en cada paquete. La longitud fija no necesita ese modelo adicional. El alfabeto, el número de símbolos y el encuadre común ya los conoce el receptor. El valor $B$ es una hipótesis de presupuesto configurable, no una serialización del diccionario.

La longitud esperada total es $nL+B$. Frente a $3n$ bits, hay ahorro cuando $$n>\frac{B}{3-L}.$$ Si el modelo se comparte entre muchos paquetes, se puede repartir su coste o poner $B=0$.

ns = np.unique(np.geomspace(1, max(4096, n_simbolos), 120).astype(int))
fig, ax = plt.subplots(figsize=(9, 4.3), layout='constrained')
resultados = []
for nombre, color in [('Huffman para q', AZUL), ('Shannon–Fano para q', NARANJA)]:
    L = medias[nombre]
    ax.plot(ns, L+cabecera_bits/ns, color=color, label=nombre+' + cabecera/n')
    total = n_simbolos*L+cabecera_bits
    minimo_n = math.floor(cabecera_bits/(3-L)+1e-10)+1
    resultados.append((nombre, f'{total:.2f}', f'{100*(1-total/(3*n_simbolos)):.2f} %', minimo_n))
ax.axhline(3, color=GRIS, ls='--', label='Longitud fija: 3 bits/símbolo')
ax.axvline(n_simbolos, color=GRIS, ls=':', label=f'Paquete elegido: n = {n_simbolos}')
ax.set(xscale='log', ylim=(0, 5), xlabel='Símbolos n por paquete', ylabel='Bits totales por símbolo',
       title=f'Presupuesto de cabecera: {cabecera_bits} bits por paquete')
ax.legend(fontsize=9); ax.grid(alpha=.2); plt.show()
print('El eje vertical se limita a 5 bits/símbolo; los paquetes más cortos pueden superar ese valor.')

Antes de mirar la explicación¶

  1. Con p1=0.4, ¿qué código tiene menor longitud media y qué eficiencia alcanza?
  2. Cambia p1 a 0.1. ¿Que gane el código dado de Shannon–Fano contradice la optimalidad de Huffman?
  3. ¿Por qué el cambio de preferencia se produce en p1=1/3?
  4. Con p1=0.4 y una cabecera de 64 bits, ¿cuántos símbolos hacen falta para ahorrar bits?
  5. ¿Puede un código con alta eficiencia aumentar el tamaño de un paquete corto?

Explicación de lo observado¶

  1. $H\simeq2.171$, $L_{\mathrm H}=2.2$ y $L_{\mathrm{SF}}=2.3$. Las eficiencias son aproximadamente 98.68 % y 94.39 %.
  2. No. Se sigue usando el Huffman construido para otra distribución. Con p1=0.1, sus longitudes medias son 2.8 y 2.45, respectivamente. Reconstruir Huffman para la nueva fuente volvería a dar un código compacto, pero esa construcción no forma parte del cuaderno.
  3. Al igualar $3-2p_1$ con $2.5-0.5p_1$ se obtiene $p_1=1/3$. Debajo de ese valor favorece a Shannon–Fano dado; encima, a Huffman dado.
  4. Para Huffman, $64/(3-2.2)=80$: la igualdad está en 80 y el ahorro estricto empieza en 81. Para Shannon–Fano, $64/0.7\simeq91.43$: se necesitan al menos 92.
  5. Sí. La eficiencia $H/L$ mide las palabras del código. La cabecera puede superar el ahorro de esas palabras si hay pocos símbolos para amortizarla.
